## 2026-10-30（第 1 天）

### 1. VS Code 打开了 Windows 侧目录，环境全对不上

- **现象**：从"最近打开"点 `study`，路径是 `C:\Users\lenovo\study`。终端里 `ros2` 命令不可用，`cp /opt/ros/...` 提示路径不存在。
- **原因**：ROS2 装在 WSL（Ubuntu 22.04）里，Windows 文件系统没有这套环境。VS Code 打开的是两套不同的文件系统。
- **解法**：所有 ROS2 相关操作都在 WSL 侧 `/home/lenovo/study` 里做。
  - 判断方法：终端执行 `pwd`，显示 `/home/...` 才对、显示 `/mnt/c/...` 就是错了。
  - 正确打开方式：WSL 终端里 `cd ~/study && code .`，并确认左下角是 `WSL: Ubuntu-22.04`。
- **耗时**：约 20 分钟

### 2. 新开终端报 `Package 'demo_nodes_py' not found`

- **现象**：第一个终端能跑，新开的终端一执行 `ros2 run demo_nodes_py talker` 就报包找不到。
- **原因**：`source` 只对**当前这个 shell** 生效，新终端是全新环境，环境变量没继承。
- **解法**：每个新终端先执行
  ```bash
  source /opt/ros/humble/setup.bash
  ```
  （可选优化：写进 `~/.bashrc` 省掉这一步，但先养成手动 source 的习惯更安全。）
- **耗时**：5 分钟

### 3. 同时开了两个终端窗口，命令敲混了

- **现象**：一个独立的终端浮窗（标题 `lenovo@LAPTOP-18V9TIKE`）+ VS Code 内置终端，两边都在敲 `source`，不清楚该用哪个。
- **原因**：Windows 侧启动的终端窗口和 VS Code 内置终端是两个会话，互不影响。
- **解法**：统一用 VS Code 内置终端（`` Ctrl+` `` 开关）。需要并行跑两个节点时用 `` Ctrl+Shift+` `` 新建，终端面板里能并排看到两个。
- **耗时**：10 分钟

### 4. 不知道官方示例的源码在哪里

- **现象**：想读 `talker.py` 源码，但 `ros2 run` 只负责运行，不知道文件在哪。
- **解法**：
  ```bash
  python3 -c "import demo_nodes_py, os; print(os.path.dirname(demo_nodes_py.__file__))"
  ```
  得到 `/opt/ros/humble/lib/python3.10/site-packages/demo_nodes_py`，话题示例在 `topics/` 下。
- **注意**：`/opt` 是系统目录，**不要直接改**（升级会覆盖），复制出来再改：
  ```bash
  mkdir -p ~/study && cp /opt/ros/humble/lib/python3.10/site-packages/demo_nodes_py/topics/*.py ~/study/
  ```
- **耗时**：10 分钟

### 5. listener 日志的时间戳挤在一起，还不是递增的

- **现象**：listener 刚启动时一次性打印 6 条，时间戳是
  `752.287 / 752.324 / 752.302 / 752.296 / 752.297 / 752.293`——全挤在几毫秒内，而且不是递增。
- **原因**：listener 启动得比 talker 晚，它一上来就把中间件缓冲区里**积压的旧消息**一次性补处理完，所以打印时刻挤在一起。缓冲区容量就是 `create_publisher` 的第三个参数 `10`（QoS 的 depth，`KEEP_LAST` 策略）。
- **结论**：观察发布频率要看 **talker 侧**输出，不要看 listener 启动瞬间。
- **遗留疑问**：为什么这 6 条的时间戳不是严格递增？待查（记录于此，后续如果搞懂再补）。

### 6. 订阅端实测频率 27Hz，不是 10Hz

- **现象**：listener 打印"实测27.1Hz"，并且 x 在 `1.15` 和 `14.25` 之间来回跳变。
- **原因**：之前用 `timeout` 结束 `ros2 run` 时，只杀掉了外层启动器，**真正的节点进程还在后台活着**。多个 talker 同时往 `/target` 发布，订阅端收到的是多路交错的帧，间隔被压到 0.037 秒。
- **判断方法**：`ros2 node list` 看看是不是有多个 `/target_publisher`。
- **解法**：
  ```bash
  pkill -f "lib/my_first_pkg/"
  ```
  ⚠️ 注意：直接写 `pkill -f my_first_pkg` 会把执行这条命令的 shell 自己也杀掉（退出码 15），必须匹配更精确的路径。
- **耗时**：15 分钟

### 7. 改了 launch 文件，`ros2 launch` 却还是旧行为

- **现象**：给 `bringup.launch.py` 加了 `namespace` 参数，`colcon build` 显示成功（0.56 秒），但 `ros2 launch ... namespace:=robot2` 后 `ros2 node list` 还是 `/node_a_sensor`，没有 `/robot2` 前缀。
- **定位过程**：
  1. 先怀疑代码写错 → `grep namespace src/.../bringup.launch.py` 有 4 处，代码没问题
  2. 再查 install 目录 → `grep namespace install/.../launch/bringup.launch.py` **没有匹配**
  3. 结论：colcon build 没有把新文件复制到 install
- **根因**：ament_python 包的 `colcon build` 是增量构建，`data_files` 里的 `launch/` 目录在这一轮没被重新安装（build/install 里有缓存）。
- **修复**：
  ```bash
  rm -rf build install log
  colcon build
  ```
  重建后 `grep -c namespace install/.../bringup.launch.py` 得到 4，launch 正常。
- **验证**：
  ```
  /robot2/node_a_sensor
  /robot2/node_b_filter
  /robot2/node_c_alarm
  /robot2/processed_distance
  /robot2/sensor_data
  ```
- **耗时**：25 分钟

### 8. `ros2 node list` 看到的是"野进程"，不是刚启动的节点

- **现象**：`ros2 launch` 因 Ctrl+C 退出（日志显示 `process has died ... exit code 1`），但 `ros2 node list` 仍然列出 3 个不带命名空间的节点。
- **原因**：`timeout` / `Ctrl+C` 只结束了 launch 主进程，**子节点进程可能残留**在后台，继续往话题发数据。
- **排查**：`ps -eo pid,etime,cmd | grep lib/my_first_pkg`
- **处理**：
  ```bash
  pkill -f "lib/my_first_pkg/"
  ```
  ⚠️ 别写成 `pkill -f my_first_pkg`，会把自己的 shell 也杀掉（退出码 15）。
- **耗时**：10 分钟
