# M1-4 ｜ 系统调优：从"能跑"到"跑得稳、跑得快"

把一条**故意写坏**的图像链路优化到达标线，并如实记录踩到的坑（见 `FAULTS.md`）。

## 一、前后对比

| 版本 | 输入 `/camera/image_raw` | 输出 `/perception/result` | 控制 `/control/cmd` | 端到端延迟 |
| :-- | :--: | :--: | :--: | :--: |
| **基线**（原始两端） | 25.4 Hz | 4.5 Hz | 4.6 Hz | 平均 1376 ms |
| **只改发布端** | 30.0 Hz | **0（收不到）** | 20.0 Hz | — |
| **只改处理端** | 25.8 Hz | 0.92 Hz | 20.0 Hz | 9 ms |
| **两端都改** | **30.83 Hz** | **30.61 Hz** | **20.80 Hz** | **平均 10 ms / 最大 32 ms** |

达标线：输入 ≥30 Hz、输出 ≥30 Hz、控制 ≥20 Hz、P95 <200 ms。

> 说明：本机 18 核，基线比题目给的参考值（15.6 / 2.3 / 2443ms）略好，但同样不达标。

**对照实验的意义**（题目验收第 5 条）：

- 只改发布端 → 输入修好了，但输出一条都收不到（QoS 不兼容，见故障 1）
- 只改处理端 → 处理快了，但输入仍卡在 25.8 Hz，输出也跟着上不去
- **两端必须同时改**

## 二、改了什么，为什么有效

### 发布端 `camera_pub.py`

| 改动 | 原版 | 现在 | 为什么有效 |
| :-- | :-- | :-- | :-- |
| 造帧 | 双重 Python 循环逐像素写 640×480（30 万次迭代） | numpy 广播向量化 | Python 循环每帧吃掉大半帧预算（33ms 里占 20ms 以上），向量化后单帧 <2ms，30Hz 才跑得稳 |
| QoS 可靠性 | `RELIABLE` | `BEST_EFFORT` | 图像是流数据，旧帧没有价值。RELIABLE 在拥塞时会重传/阻塞发送 |
| QoS 深度 | `depth=30` | `depth=2` | 30 帧 × 921KB ≈ 27MB 积压在队列，延迟直接堆到秒级 |
| 编码 | `bgr8`（921KB/帧） | `mono8`（307KB/帧） | 下游只做灰度处理，彩色信息是纯浪费。带宽省 2/3 |

### 处理端 `image_proc.py`

| 改动 | 原版 | 现在 | 为什么有效 |
| :-- | :-- | :-- | :-- |
| 工作分辨率 | 先放大到 1280×720 处理，再缩回 640×480 | 直接在 640×480 处理 | 原版把计算量白放大 3 倍（题目明确允许改分辨率） |
| 提亮 + 对比度 | 两个双重循环，92 万像素 × 2 遍 | `np.clip` 向量化 | 原版单帧约 400ms，这是输出只有 2.3Hz 的直接原因 |
| 订阅 QoS | `RELIABLE` + `depth=30` | `BEST_EFFORT` + `depth=1` | 延迟累积的根因是**队列排队**不是单帧慢。depth=1 只留最新帧，旧的直接丢 |
| 执行器 | `SingleThreadedExecutor` | `MultiThreadedExecutor(num_threads=2)` | 单线程时图像回调（几百毫秒）把控制定时器的回调堵死，控制因此只有 2.3Hz |

### 定时器留余量（容易忽略的一环）

`create_timer(1/30)` 的**实际周期是「设定值 + 回调开销」**，所以直设 1/30 只能跑出 29.9Hz，
差一点点不达标。给 3~4% 余量后实测落在目标之上：

| 定时器 | 原写法 | 实际跑出 | 改成 | 实际跑出 |
| :-- | :--: | :--: | :--: | :--: |
| 相机 30Hz | `1/30` | 29.9 Hz | `1/(30*1.03)` | **30.83 Hz** |
| 控制 20Hz | `1/20` | 19.9 Hz | `1/(20*1.04)` | **20.80 Hz** |

这不是"凑指标"——Python 定时器本来就有固定开销，工程上补偿调度延迟是常规做法。

### 保持不变（题目硬性要求）

- 处理语义：转灰度 → 提亮 +20 → 对比度 `(v-128)*3/2+128`
- 输出 640×480 `mono8`
- **输出 `header.stamp` 沿用输入**（重新打时间戳会让 `ros2 topic delay` 假性归零）

## 三、牺牲了什么

| 牺牲项 | 代价 | 为什么值得 |
| :-- | :-- | :-- |
| **彩色信息** | 输入从 `bgr8` 降为 `mono8`，链路里再也没有颜色 | 下游只输出灰度，彩色在链路上是纯带宽浪费 |
| **不丢帧** | QoS 改 `BEST_EFFORT` + `depth=1`，拥塞时**主动丢旧帧** | 图像处理里"最新的帧"比"完整的帧序列"重要。丢帧换低延迟 |
| **工作分辨率** | 去掉 1280×720 中间步骤，全程 640×480 | 原版放大再缩小是纯浪费，输出本来就要 640×480 |
| **单线程简单性** | 改用多线程执行器，多一层并发复杂度 | 不换的话控制回调永远被图像回调堵住 |

**核心权衡：宁可丢帧，不能延迟。** 赛场上一帧 2 秒前的图像比没有图像更危险。

## 四、怎么复现

```bash
cd ~/study/M1/M1-4
source /opt/ros/humble/setup.bash

# 终端1：相机（它自己每 3 秒报一次真实频率）
python3 camera_pub.py

# 终端2：处理链路
python3 image_proc.py

# 终端3：测量
ros2 topic hz /perception/result      # 期望 ≈30 Hz
ros2 topic hz /control/cmd            # 期望 ≈20 Hz
ros2 topic delay /perception/result   # 期望 P95 < 200ms
```

> `ros2 topic hz /camera/image_raw` 会与链路抢资源，读数偏低。**输入频率以终端1 自己打印的 `[CAMERA]` 为准。**

## 五、处理语义验证

用同一张输入图分别跑"原版逐像素算法"和"向量化算法"，逐像素比对：

```
逐像素算法 vs 向量化算法 完全一致: True
差异像素数: 0
输入 mean 127.4 -> 输出 mean 147.0
```

**输出内容与原语义完全相同**，只是算得更快——不是"直接转发原图"。

## 六、接口契约

| 名称 | 类型 | 方向 |
| :-- | :-- | :-- |
| `/camera/image_raw` | `sensor_msgs/Image`（`mono8` 640×480） | 输入 |
| `/perception/result` | `sensor_msgs/Image`（`mono8` 640×480） | 输出 |
| `/control/cmd` | `geometry_msgs/Twist` | 20 Hz |

**输入编码由 `bgr8` 改为 `mono8`**（题目允许），`image_proc.py` 已适配。
